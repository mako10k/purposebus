# Purposeライフサイクル 仮要件 r1

2026-09-30 / Draft・未承認 / 要件作成と机上検討のみ

## 目的と根拠

Publisherが「依頼したが誰も受け取っていない」「読まれたが受理されていない」「結果が届いたが達成を確認していない」を判別でき、Subscriberが曖昧さを解消してから引き受け、双方が同じPurposeの変更と結果を追えることを目指す。

根拠は本チャットの所有者指示：Publisher/Subscriber双方のPurpose・参加状態・途中/最終結果の読み書き、フィロソフィーと実行形態の分離、四つの実行環境、今回の「仮に要件を固め」「机上…シミュレーション」「多くない状態ややり取り」。以下の具体的選択は著者の仮置きであり、所有者承認ではない。

既存 `docs/requirements.md` と Accepted ADR `docs/adr/0001-add-local-read-only-mcp.md` の1.0.0契約を変更しない。独立したPurpose管理は次期候補であり、既存のMessage、Delivery ack、Request fulfilledを受理・達成と読み替えない。次期バージョン、外部公開、API、保存形式、通知方式、実装計画は未決定。

## 少ない状態と、別に保持する事実

| 軸 | 状態 | 意味 |
|---|---|---|
| Purpose全体 | 募集中（open） | 参加・質問・変更・結果検証を受け付ける。作業中や検証待ちもここに含む |
| Purpose全体 | 達成（completed） | 指定された評価者が現行版の達成条件を満たすと確認した |
| Purpose全体 | 撤回（withdrawn） | Publisherが依頼を終了した。実行停止の確認とは別 |
| Subscriberの参加 | 検討中（considering） | 読み出しを報告したが、現行版の作業を引き受けていない |
| Subscriberの参加 | 受理（accepted） | 特定版・範囲の作業を引き受けた。実行開始や成功を意味しない |
| Subscriberの参加 | 終了（finished） | 引き受けた作業を終えた。成功・失敗・取消・中断を結果理由として保持する |
| Subscriberの参加 | 辞退（declined） | 検討して引き受けないと表明した |

未読は参加レコードがないこととして表す。「明確化待ち」「実行中」「結果検証待ち」「実行環境待ち」をこの状態表へ追加しない。未解決質問、開始/停止の観測、途中/最終結果、評価判断、最終更新時刻を別の事実として表示する。利用者にはたとえば「募集中／受理0／検討中1／未解決質問1」と見せる。古い観測から稼働中・停止済みを断定しない。

## 仮要件

- PL-01：Purposeには安定したID、Publisher、内容の版、目的、達成条件、許可された作業範囲、評価者と達成判定方式を保持する。曖昧な初期内容でも公開できる。未定事項は未定と表示し、空欄から実行許可を推定しない。受理時には当人の範囲・条件・権限を説明できなければ質問する。
- PL-02：内容を読むだけの操作は状態を変更しない。「読んだ」という報告は明示的な行為で、理解や受理の証明にはしない。質問・受理・辞退は読んだ版の報告を同時に含められるため、別の受領報告を必須にしない。Publisherには報告したSubscriberと版を一覧表示する。報告していない閲覧者の存在は分からないと表示する。
- PL-03：Subscriberは自分の参加状態、担当範囲、未解決質問、途中/最終結果を読み書きする。他者の参加・結果を上書きできない。Publisherは全体を読み、Purpose変更・撤回・達成判断を行う。全体状態の書き込みは意味のある操作に限定し、参加者の事実を消さない。権限は実行環境の能力と別に管理する。
- PL-04：質問には対象版、質問者、問い、回答と解消確認を結び付ける。質問への返信だけでは内容の版を増やさない。目的・範囲・達成条件・権限が変わる回答は、Purposeの改版を伴う。回答者が一方的に「解消済み」にしない。質問者は受理または継続確認と同時に質問を解消できる。
- PL-05：未解決質問は受理前にも受理後にも持てる。受理後の質問には、依存する作業を待つのか、既に許可された独立範囲を続けるのかを明示する。追加質問で受理を自動取消しせず、質問中の新しい範囲を自動実行しない。
- PL-06：改版時は既存の受理を現行版の受理と数えない。旧版の受理・成果は保持し、関係者は現行版を明示的に再確認する。変更影響の自動判定はr1に含めず、仮置きでは全受理者に再確認を求める。未確認の間は変更後の作業を開始せず、旧作業を止める必要と停止観測を表示する。
- PL-07：途中結果を何度でも共有でき、最終結果提出と参加終了を一つの行為にできる。結果にはPurpose版・参加者・担当範囲・結果区分・根拠を結び付ける。結果は追記/訂正履歴を保持し、旧成果を消さない。最終提出だけでPurposeを達成にしない。評価者の判断と根拠を記録する。
- PL-08：仮置きの既定は「Publisherが評価者、現行版の一つの適合結果で達成可能」。全員成功が必要な依頼では、受理者が増えるたび変動する集合ではなく、必須担当の集合をPurposeに指定する。判定方式の変更は改版と再確認を伴う。未定の方式では達成を宣言できない。達成判断に影響する未解決質問がある場合も、達成を宣言できない。全ての雑談や任意の追加質問の解消を必須にするのではなく、どの条件の判断を妨げるかを明示する。
- PL-09：撤回は新規受理・新規作業を止める依頼の終了宣言である。既存作業の停止要求、停止確認、停止未確認を別に追える。遅れて届いた途中/最終結果は対応版の履歴に残すが、撤回を達成に変更しない。Publisherは残っている作業・未確認状態と結果を読める。
- PL-10：達成時にも残存作業が自動停止したとは扱わない。必要な停止は明示的に要求・確認する。達成/撤回後の追加依頼は、関係を示した新Purposeで扱う。終了済み履歴の再開はr1では採用しない。
- PL-11：辞退・終了後に同じSubscriberが再参加する場合は新しい参加試行として記録し、過去の試行を維持する。評価不適合後の再作業も、Purposeが募集中なら新しい試行として受理できる。途中結果だけを残して最終提出しない終了も、理由を表示できる。
- PL-12：重複した同じ意思表明は一回分として扱う。古い版・古い試行の遅延イベントが現行の受理・評価・状態を更新しない。履歴として取り込むか競合として返すかを利用者が判別できる。連絡途絶は辞退/失敗/停止と断定せず、最終観測時刻と不明を表示する。
- PL-13：同一のSubscriber識別子を使う複数セッションは人数を水増ししない。セッション/実行試行と参加者を区別する。人間とAIの両方を参加者にできる。既存Partitionの範囲を守り、他ユーザー・他ホスト間通信をこの候補だけで許可しない。
- PL-14：両者がPurposeの有無・内容・版・全体状態を読める。Subscriberは許可された共有結果を読める。仮置きは同一Purpose参加者に共有可能な結果のみを登録し、秘密の非公開結果共有は別要件とする。削除/保存期間・通知漏れ時の再取得の詳細は次段階で決める。
- PL-15：フィロソフィー側が目的、受理、明確化、改版、評価、撤回、再試行の判断を保持する。実行形態側は可能な操作・制約・観測を返す。能力不足や未確認を「達成」「停止済み」に変換しない。起動権限がなければ参加を検討できても起動しない。

## 最小のやり取り

明確な依頼：公開 → 受理（読了報告を含む）→ 最終結果と参加終了 → 評価者が達成確認。状態を変える業務行為は4回、閲覧は随時可能。

曖昧な依頼：公開 → 質問（読了報告を含む）→ 回答/改版 → 受理（現行版と質問解消確認）→ 最終結果と参加終了 → 達成確認。業務行為は6回。回答が不十分なら質問の追記を繰り返せる。質問数を固定したり、往復回数を達成条件にしたりしない。

## 次の所有者判断

1. 全体3状態・参加4状態に質問/結果/実行観測を添える構造を採るか。
2. 既定の達成判定を「Publisherが一つの適合結果を確認」とするか、依頼ごとに必須指定とするか。
3. 全改版で再確認、終了済みPurposeへの追加は新Purpose、撤回は停止確認と別、という保守的な仮置きを採るか。

代替は影響のない改版を自動承継する、終了済みPurposeを再開する、停止を確認できるまで全体を終了させない、など。いずれも追加の判断・競合規則が必要になる。r1では状態数と履歴の明確さを優先して上記を仮置きした。

## 現段階の完了条件とレビュー境界

双方の要求を上記PL要件に対応させ、別紙の具体的な会話と状態追跡で矛盾・残る判断を示すことが今回の完了条件。所有者の受理、基本設計、実装や実環境での成立は含まない。

自己点検：Publisher要求はPL-02/03/06/07/09、Subscriber要求はPL-01/03/04/07/14、少ない状態と明確化はPL-04/05、実行形態分離はPL-15に対応。最大の弱点は「全改版で再確認」の操作負担と、共有範囲の限定である。机上結果は挙動の説明可能性だけを支持する。

提案する独立レビュー範囲：この要件と別紙の固定スナップショットについて、所有者要求との欠落/矛盾、状態と行為の整合、曖昧さ解消の操作負担、版と撤回の競合を確認する。API/DB/コード/性能/プラットフォーム実装は後続設計の範囲。所有者が候補とこの範囲を確認する前に、正式な独立レビューやAccepted化を行わない。
